# Runbook — running one pilot question with workflow B (the skill) as the main agent

This is the exact operator procedure used for the 2026-09-03 Stage B runs. The main agent (the chat session) plays the role SKILL.md gives it; role agents are launched with the Agent tool, `model: "sonnet"`, `subagent_type: general-purpose`, one per prompt. Judges use `model: "opus"`. Paths below assume the repo root; `S` = `skill/deep-research/scripts`, `Q` = a question id such as `business-finance-3`, `B` = `eval/private/results/<date>-B`.

1. **Init and brief.** `python3 S/ledger.py --run B/Q init --question "<question text from eval/private/questions/Q.json>" --slug Q --preset standard --mode report`. Write `B/Q/00-brief.md` yourself from `skill/deep-research/prompts/brief.md`: 4 angles, each with hypothesis, disconfirmer and 3 first queries; sources per angle per round 4; max rounds 2.
2. **Round 1.** Launch one researcher per angle in parallel: fill `skill/deep-research/prompts/researcher.md` with absolute paths, the angle, hypothesis, `SOURCE_TARGET` 4, round 1. Since 2026-09-10 the prompt itself carries the stop rule (stop at the target, never exceed it by more than one), the `--round` on `claim add`, the ledger-file rules (no direct edits, no placeholder commands, heredocs) and the per-angle central cap (16, env `DEEP_RESEARCH_ANGLE_CENTRAL_CAP`); nothing needs adding to the fill. Record each agent's reported token usage in `B/tokens.json` (per-agent map; generation vs judge keys).
3. **Re-decompose.** `python3 S/ledger.py --run B/Q state --format md` and the `## Gaps` sections of `B/Q/angles/*.md`. Append 1-2 round-2 angles to the brief (seeded by gaps; drop saturated angles) and launch those researchers with round 2. Stop after round 2 (standard).
4. **Verify.** `python3 eval/make_batches.py --run B/Q` (after round 1; run again with `--round 2 --start <next>` after round 2, or once at the end). Launch one verifier per batch file with `skill/deep-research/prompts/verifier.md` filled (label v1, v2, …; the prompt tells the verifier to read its batch file). Verifiers never set labels. If agents die (rate limit), just re-run `make_batches.py`: it lists only still-unchecked claims. Use a new `--start` so verifier labels stay distinct, and keep the `--round` filter if round 2 is still being researched, otherwise the rebuilt batches overlap the later round-2 batches (observed 2026-09-04, ~150k duplicate tokens). After the last round, run `make_batches.py` once more with no `--round` filter and a fresh `--start` as a safety net: before 2026-09-10 a claim registered by a round-2 researcher on a round-1 source was stored with round 1 and missed both builds (observed 2026-09-04, 8 claims); the researcher prompt now passes `--round` on `claim add`, so the final build should report 0 central claims. Verifiers now grade every source they add; check `sources.md` for empty Grade cells before writing and grade stragglers from the main session.
5. **Write.** `python3 S/ledger.py --run B/Q render`; launch the writer with `skill/deep-research/prompts/writer.md` filled with `LENGTH_TARGET` 1500 (it writes `outline.md` with per-section word budgets first, reads the claim list via `ledger.py claims list --format md`, `sources.md`, `verification.md`, and self-checks with `cite_check.py --no-network` before finishing). Record the first-draft word count from the writer's report to see whether draft-then-cut is gone. If the question or the brief asks for a presentation element (a dated timeline, a comparison table), add one line to the writer fill saying so: on 2026-09-10 the writer read the brief's line about the timeline and still did not produce one, which cost a rubric item and a 46k presentation pass (resume the writer in place with SendMessage, snapshot `report-before-*.md` and `judge-before-*.json` first, re-judge).
6. **Citation pass.** `python3 S/cite_check.py --run B/Q` (with network). Errors go back to a writer fix pass; warnings are recorded (`health-unknown` means the archive lookup failed, not that the URL is dead; re-run later). Then read the `central-claim-unused` list: if a failed rubric item's fact is in it, run a writer coverage pass (snapshot first) and re-judge; if the fact is not in the ledger at all, record it as a recall failure and do not add new retrieval after judging. Then `python3 S/ledger.py --run B/Q finalize --harness claude-code --model claude-sonnet-5 --agents <n> --rounds 2 --execution parallel --tokens <sum of generation tokens>`.
7. **Judge.** Launch an Opus judge with `eval/prompts/judge.md` semantics: it reads `eval/private/questions/Q.json` and `B/Q/report.md`, writes `B/Q/judge.json`. Compute compliance with `eval/score.py` (never trust the judge's own arithmetic). Keep pre-edit snapshots (`report-before-*.md`, `judge-before-*.json`) whenever a pass is re-judged.
8. **Baseline A.** The user runs `/deep-research "<question>"` in Claude Code, saves the returned report as `eval/private/results/<date>-A/Q/report.md` (plus stats as `run.json`), then `python3 eval/cite_audit.py <report> --out .../cite.json` and an Opus judge writes `judge.json`. `python3 eval/score.py --questions eval/private/questions --a <A dir> --b <B dir>`.

Costs observed at `standard`: 2026-09-10 afternoon (culture-history-3, skill v1.1 with the un-numbered researcher prompt, none of 16 agents killed): 1.85M Sonnet tokens (research 601k, verification 1.04M for 63 central claims in 9 batches, writing 210k) plus a 46k presentation pass, compliance 0.966 first pass and 1.00 after the pass, 45 min wall clock. 2026-09-10 morning (culture-history-3, skill v1.1): 2.17M Sonnet tokens known (research 637k, verification 1.26M for 80 central claims in 11 batches, writing 271k) plus five verifiers killed by a network error, compliance 1.00 first pass; the central count rose to 80 because the prompt named the 16-per-angle cap (removed since). 2026-09-04 (culture-history-3, with the central cap and "stop at 4 sources; never exceed 5" in the researcher prompt): 1.85M Sonnet tokens (research 600k, verification 970k for 59 central claims in 9 batches, writing 280k, no coverage pass), compliance 1.00. Earlier the same day (BF3, PL3, cap but no stop rule): 2.1M and 2.3M Sonnet tokens per question (research 630-870k, verification 1.3-1.5M, writing 210-350k plus a 140k coverage pass); the per-source cap did not reduce the central count because researchers over-fetch. Earlier (2026-09-03): 1.5-2.6M Sonnet tokens per question before the central cap; research 420-730k, verification 790k-1.34M, writing 290-530k; judging 50-60k Opus per report. A session rate limit was hit after ~3.5M tokens in one afternoon.
