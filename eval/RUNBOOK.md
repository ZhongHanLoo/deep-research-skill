# Runbook — running one pilot question with workflow B (the skill) as the main agent

This is the exact operator procedure used for the 2026-09-03 Stage B runs. Since 2026-09-11 `eval/fill_prompts.py` fills every role prompt from files (`researcher` parses the angle's hypothesis and disconfirmer from the brief; `verifier` hands off the batch file; `writer` hands off the claim list; `judge` writes the hand-off wrapper) and refuses to leave a placeholder; write the filled files under the private results tree (for example `B/prompts-Q/`) and hand each to its agent as "cat this file and follow it". The main agent (the chat session) plays the role SKILL.md gives it; role agents are launched with the Agent tool, `model: "sonnet"`, `subagent_type: general-purpose`, one per prompt. Judges use `model: "opus"`. Paths below assume the repo root; `S` = `skill/deep-research/scripts`, `Q` = a question id such as `business-finance-3`, `B` = `eval/private/results/<date>-B`.

1. **Init and brief.** `python3 S/ledger.py --run B/Q init --question "<question text from eval/private/questions/Q.json>" --slug Q --preset standard --mode report`. Write `B/Q/00-brief.md` yourself from `skill/deep-research/prompts/brief.md`: 4 angles, each with hypothesis, disconfirmer and 3 first queries; sources per angle per round 4; max rounds 2.
2. **Round 1.** Launch one researcher per angle in parallel: fill `skill/deep-research/prompts/researcher.md` with `python3 eval/fill_prompts.py researcher --run B/Q --question-file eval/private/questions/Q.json --angle <slug> --round 1 --out B/prompts-Q/r1-<slug>.md` (source target 4 by default; the hypothesis and disconfirmer come from the brief). Since 2026-09-10 the prompt itself carries the stop rule (stop at the target, never exceed it by more than one), the `--round` on `claim add`, the ledger-file rules (no direct edits, no placeholder commands, heredocs) and the per-angle central cap (16, env `DEEP_RESEARCH_ANGLE_CENTRAL_CAP`); nothing needs adding to the fill. Record each agent's reported token usage in `B/tokens.json` (per-agent map; generation vs judge keys).
3. **Re-decompose.** `python3 S/ledger.py --run B/Q state --format md` and the `## Gaps` sections of `B/Q/angles/*.md`. Append 1-2 round-2 angles to the brief (seeded by gaps; drop saturated angles) and launch those researchers with round 2. Stop after round 2 (standard).
4. **Verify.** `python3 eval/make_batches.py --run B/Q` (after round 1; run again with `--round 2 --start <next>` after round 2, or once at the end). Launch one verifier per batch file with `skill/deep-research/prompts/verifier.md` filled (label v1, v2, …; the prompt tells the verifier to read its batch file). Verifiers never set labels. If agents die (rate limit), just re-run `make_batches.py`: it lists only still-unchecked claims. Use a new `--start` so verifier labels stay distinct, and keep the `--round` filter if round 2 is still being researched, otherwise the rebuilt batches overlap the later round-2 batches (observed 2026-09-04, ~150k duplicate tokens). After the last round, run `make_batches.py` once more with no `--round` filter and a fresh `--start` as a safety net: before 2026-09-10 a claim registered by a round-2 researcher on a round-1 source was stored with round 1 and missed both builds (observed 2026-09-04, 8 claims); the researcher prompt now passes `--round` on `claim add`, so the final build should report 0 central claims. Verifiers now grade every source they add; check `sources.md` for empty Grade cells before writing and grade stragglers from the main session.
5. **Write.** `python3 S/ledger.py --run B/Q render`; launch the writer with `skill/deep-research/prompts/writer.md` filled with `LENGTH_TARGET` 1500 (it writes `outline.md` with per-section word budgets first, reads the claim list via `ledger.py claims list --format md`, `sources.md`, `verification.md`, and self-checks with `cite_check.py --no-network` before finishing). Record the first-draft word count from the writer's report to see whether draft-then-cut is gone. Since 2026-09-10 (after the v1.1 tag, not yet re-tested) `prompts/writer.md` itself tells the writer to give any presentation element the question or brief asks for (a dated timeline, a comparison table) its own outline section, budget and place in the report; confirmed once on 2026-09-10 evening (technology-3: the writer gave a definitions table its own section from the prompt alone), so the operator line is no longer required; it is still harmless to add one when the element is unusual, because on 2026-09-10 afternoon the writer read the brief's line about the timeline and did not produce one, which cost a rubric item and a 46k presentation pass (resume the writer in place with SendMessage, snapshot `report-before-*.md` and `judge-before-*.json` first, re-judge).
6. **Citation pass.** `python3 S/cite_check.py --run B/Q` (with network). Errors go back to a writer fix pass; warnings are recorded (`health-unknown` means the archive lookup failed, not that the URL is dead; re-run later). Then read the `central-claim-unused` and `supporting-claim-unused` lists (the second, added 2026-09-10, names unused supporting claims that carry a number, grade or recommendation): if a failed rubric item's fact is in either, run a writer coverage pass (snapshot first) and re-judge; if the fact is not in the ledger at all, record it as a recall failure and do not add new retrieval after judging. Then `python3 S/ledger.py --run B/Q finalize --harness claude-code --model claude-sonnet-5 --agents <n> --rounds 2 --execution parallel --tokens <sum of generation tokens>`.
7. **Judge.** Launch an Opus judge with `eval/prompts/judge.md` semantics: it reads `eval/private/questions/Q.json` and `B/Q/report.md`, writes `B/Q/judge.json`. Compute compliance with `eval/score.py` (never trust the judge's own arithmetic). Keep pre-edit snapshots (`report-before-*.md`, `judge-before-*.json`) whenever a pass is re-judged.
8. **Baseline A.** With the user's explicit go-ahead in their own words (the Workflow tool needs it), the main session launches the built-in workflow as `Workflow({name: 'deep-research', args: '<question text from the private file>'})` with its constants untouched, as on 2026-09-04/05 (progress #40-#41): a fresh run launches about 100 agents and about 3.7M tokens, which did not fit one subscription window twice; when agents die on the session limit, relaunch after the reset with `resumeFromRunId` (the cache replays completed stages; it completed on the third attempt). Save the returned object as `eval/private/results/<date>-A/Q/result.json`, the workflow output with logs as `workflow-output.json`, a mechanical Markdown rendering of the JSON (summary, findings with evidence and source URLs, caveats, open questions, refuted claims, source list; no wording changed, a header line saying so) as `report.md`, and attempts, tokens and stats as `run.json` (`tokens` = the completing attempt; all attempts in a note), then `python3 eval/cite_audit.py <report> --out .../cite.json` and an Opus judge writes `judge.json`. `python3 eval/score.py --questions eval/private/questions --a <A dir> --b <B dir>`. **Model:** the built-in script sets no model, so its agents inherit the session model (the 2026-09-04/05 run silently ran on Fable, found 2026-09-11); to run it on Sonnet as REQ 4 requires, copy the script the harness persists under the session's `workflows/scripts/`, add `model: "sonnet"` to its five `agent()` call sites (scope, search, fetch, verify, synthesize), change nothing else, launch with `scriptPath`, and keep the copy and its diff in the A folder (done 2026-09-11 for technology-3; that Sonnet run completed 109 agents and 4.65M tokens in one window).
